# Changelog

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.0.0/),
проект следует семантическому версионированию (SemVer).

## [Unreleased]

### Added
- `Web2App.entitlements(completion:)` (WEB-2480): все записи о доступе (`grants`,
  `activeGrant`, `testMode` ответа) и различимая причина отказа
  `EntitlementsError` — `.notConfigured`, `.noGuid`, `.network`, `.http(код)`,
  `.badResponse`. «Записей нет» — успех с пустым списком. При `.network` / `.http`
  не отнимайте доступ у покупателя — спросите позже. В `switch` по
  `EntitlementsError` добавляйте общую ветку (`default:` / `case .failure:`):
  в следующих версиях могут появиться новые причины.
- `Web2App.handleReturnURL(_:completion:)` (WEB-2479): то же, что
  `handleReturnURL(_:)`, плюс доступ после возврата.

### Changed
- **`identify(deepLinkValue:)` с кодом всегда обменивает код** (WEB-2479), даже если
  guid уже сохранён, и может сменить `currentGuid()` — если храните наш guid на своём
  сервере, передайте ему новый. Раньше сохранённый guid отдавался без обмена, и
  покупатель, оплативший в обычном браузере после показа пейвола в приложении,
  видел «не оплачено». Код уже погашен или просрочен (ответ сервера 404), а guid
  сохранён — успех с сохранённым guid (запись `identify.code_rejected_cached_guid`
  в журнале); сбой сети — ошибка `.network`. Если под прежним guid была своя покупка
  из окна SDK, а код ведёт на другую, после перезаписи видна новая; прежнюю
  возвращает восстановление по почте.
- **`identify(deepLinkValue:)` с кодом каждый раз ходит в сеть** (WEB-2479). Раньше
  при сохранённом guid вызов отвечал сразу и без сети. Теперь без сети — ошибка
  `.network` (а не сохранённый guid), и каждый вызов тратит запрос из лимита
  10 обменов в минуту. Передавайте код, только когда он новый (MMP вроде AppsFlyer
  отдаёт одно и то же значение при каждом запуске — не зовите `identify` с ним на
  каждом старте); при `.network` продолжайте с `Web2App.currentGuid()`. Доступ
  покупателя это не задевает: `entitlement` читает сохранённый guid. Пример в
  README («Быстрый старт», шаг 2) поправлен.
- **Возвратный метод обменивает код, если окно SDK не открыто** (WEB-2479):
  покупатель, который платил в обычном браузере и вернулся кнопкой с экрана после
  оплаты, получает доступ. Окно SDK открыто — закрыть его и проверить право
  (до ≈10 с) по сохранённому guid: действующая запись есть — код не тратится, как
  раньше; действующей нет, а код в ссылке есть (покупатель бросил окно SDK и оплатил
  в обычном браузере) — код обменивается. Эта проверка ходит в сеть и у перегрузки
  `handleReturnURL(_:)` без колбэка. Оговорка: если вебхук об оплате в окне SDK
  опоздал больше чем на ≈10 с, библиотека не видит доступа и обменивает код —
  доступ всё равно придёт, но ссылка из письма «оплата прошла» (например, чтобы
  открыть приложение на втором устройстве) после этого погаснет: код одноразовый.
- **`completion` у `openWebPaywall` получает доступ и после обмена кода**
  (WEB-2479): ожидание оплаты опрашивает право по текущему guid (если возвратный
  метод обменял код и guid сменился — по новому), а результат возвратного метода
  приходит и в `completion` исходного `openWebPaywall`. Каждый колбэк — ровно один
  раз.
- **`entitlement` отдаёт первую действующую запись** (WEB-2480), а если действующих
  нет — самую новую, как раньше. Раньше бралась только самая новая: неактивная
  свежая запись (возврат разовой докупки, истёкшая) прятала действующую подписку.
  Приложение, читающее `level` / `priceId`, теперь видит уровень действующей покупки.
  То же правило — в ожидании после показа пейвола.

## [0.8.1]

### Changed
- **Предзагрузка работает и у неопознанного пользователя** (`identify` вернул
  `needsEmailFallback`, органическая установка). Раньше (0.8.0) без guid
  `preloadPaywalls` ничего не делал. Теперь страницы грузятся под временный
  guid (UserDefaults; `identify` его не видит — опознание по отпечатку и
  восстановление по email не ломаются). Настоящим он становится при первом
  показе страницы. Опознали позже — фоновые страницы перегружаются под
  настоящий guid сами. Повторный вызов после первого показа, который советовала
  0.8.0, больше не нужен, но и не вредит.
- Временный guid привязан к profile-id Adapty/RevenueCat, под который создан:
  `preloadPaywalls` с другим непустым profile-id выпускает новый временный guid,
  показ с другим profile-id прежний временный guid настоящим не делает.
  Показ без profile-id (например, квиз) берёт временный guid, только если тот
  ни к какому профилю не привязан. Вызов `preloadPaywalls` без profile-id
  сменой профиля не считается.
- `clearPreloadedPaywalls()` стирает и временный guid. Настоящий guid не
  трогается, как и раньше: если пользователь уже открывал страницу (пейвол или
  квиз) или `identify` успешно его опознал, его guid сохранён и остаётся.
- Предзагруженная страница показывается, только если guid, под который она
  загружена, совпал с guid показа (по нему идёт опрос доступа); иначе показ
  идёт обычным путём.
- Журнал SDK: `paywall.preload_no_guid` больше не пишется. Новые записи:
  `paywall.preload_provisional_guid`, `paywall.preload_provisional_guid_reissued`,
  `paywall.preload_reload_guid`, `paywall.preload_guid_mismatch`,
  `paywall.preload_clear`, `guid.adopted_on_show`,
  `guid.provisional_discarded_profile_changed`.
- Манифест приватности объявляет доступ к UserDefaults
  (`NSPrivacyAccessedAPICategoryUserDefaults`, причина `CA92.1`).

## [0.8.0]

### Added
- **Предзагрузка встроенных пейволов: `Web2App.preloadPaywalls(paywallIds:…)`.**
  Страницы грузятся в фоновых WKWebView, и `openWebPaywallEmbedded(paywallId:)`
  с теми же email/profile-id показывает готовую страницу мгновенно, без
  белого экрана. После показа инстанс пересоздаётся. Если инстанс не подошёл
  (другие параметры, старше часа, ошибка загрузки, нехватка памяти), показ
  идёт прежним путём. `Web2App.invalidatePreloadedPaywalls(paywallIds:)`
  выгружает отдельные пейволы (в этой сессии уже не покажем — не держим
  WebView в памяти), `Web2App.clearPreloadedPaywalls()` — все.
- Контракт с вебом: предзагруженная страница открыта с `preload=1`, момент
  показа — `window.__web2appShown` + событие `web2app:shown`. Веб-часть
  контракта сервис поддерживает: просмотр (`PAYWALL_VIEW`), пиксели и замер
  скорости уходят только после сигнала показа — предзагрузка статистику не
  завышает.
- Без guid (`identify` вернул `needsEmailFallback`) `preloadPaywalls` ничего не
  делает (`paywall.preload_no_guid`) — позовите снова, когда
  `Web2App.currentGuid()` станет не nil. После каждого показа (с любым исходом) предзагрузка
  пейвола запускается снова; не нужен — `invalidatePreloadedPaywalls`.

### Changed
- Встроенный показ (пейвол и квиз) рисует индикатор, пока страница грузится,
  а не пустой белый экран. Если iOS выгрузила процесс страницы на экране,
  страница перезагружается.

## [0.7.1] — 2026-08-14

### Changed
- **Окно попыток опознания по отпечатку — 2 часа с первой неудачи (WEB-1384).**
  Слепок на сервере живёт максимум 2 часа, поэтому после истечения окна
  `identify(deepLinkValue: nil)` больше не ходит в сеть и сразу отдаёт
  email-фолбэк (в журнале — `identify.fingerprint_window_expired`). Повторные
  попытки ВНУТРИ окна сохранены: сценарий «увидел email-экран → закрыл →
  вернулся через 10 минут» по-прежнему склеивается. По мотивам вопроса
  интегратора «не делать лишней работы на каждом запуске».

## [0.7.0] — 2026-08-13

### Added
- **Бесшовное опознание по отпечатку устройства (WEB-1213).** `identify(deepLinkValue: nil)`
  перед email-фолбэком пробует получить guid по отпечатку: приложение отправляет
  сигналы устройства (версия iOS, модель через uname, экран в логических пунктах,
  таймзона, язык) на `POST /public/handoff/resolve-by-fingerprint`; сервер отвечает
  guid только при **единственном уверенном совпадении** с сигналами, которые
  веб-страница оставила в момент ухода покупателя в App Store. Любой промах —
  прежний email-фолбэк, поведение не хуже старого. Закрывает единственный
  небесшовный сценарий: iOS + установка после оплаты + без MMP-трекера
  (Universal Link установку не переживает, Install Referrer у Apple нет).
  Никаких IDFA/IDFV/ATT; сигналы не входят в required-reason API.
  В журнале SDK видно: `identify.fingerprint_attempt` → `identify.fingerprint_matched`
  (с `matchMethod`) или `identify.fingerprint_no_match`.

## [0.6.0] — 2026-08-13

### Added
- **Удалённый журнал SDK (`SdkLogger`).** Каждый внутренний шаг SDK —
  `configure`, ветки `identify` (кэш-guid / резолв токена / email-fallback),
  запрос права, открытие пейвола/квиза, события JS-моста, возвратный deep-link,
  APP_INSTALLED-callback и все ошибки сети с HTTP-кодами — теперь пачками
  отправляется на наш бэкенд (`POST /public/sdk-logs`) и дублируется в
  Xcode-консоль (`print` с префиксом `[Web2App]`). Это диагностика интеграций:
  раньше «что происходит внутри приложения интегратора» было видно только по
  логам Xcode с его стороны. Отправка fire-and-forget с дебаунсом 3 с и капом
  буфера — сбой сети или бэкенда никак не влияет на работу SDK. PII не уходит:
  email не логируется (только факт «email передан»), guid — наш собственный
  client-held идентификатор.

### Changed
- **Уточнено поведение связки `guid` ↔ profile-id на стороне сервера** (только
  документация; поведение SDK не менялось). Страница пишет значение лишь в
  ПУСТОЙ слот: заменить уже сохранённое через страницу нельзя (только серверной
  ручкой `POST /s2s/v1/identity/link-profile`), а дописать вторую платформу
  можно только вместе с верными значениями всех уже занятых слотов. Отказ
  молчаливый — сервер отвечает «успех» в любом случае (защита от перебора
  плательщиков). **Рецепт для интеграторов:** передавать ОБА идентификатора
  (`adaptyProfileId` и `revenuecatProfileId`) при КАЖДОМ открытии страницы —
  прежняя формулировка «связку с guid делает сервер сам, отдельную ручку звать
  не надо» (запись 0.5.0 ниже) вводила в заблуждение. Отдельно: наш `guid`
  нельзя использовать как profile-id платформы (`Purchases.logIn(<guid>)`) —
  с ним дозапись второй платформы через страницу не сработает никогда.
- **Исправлен образец интеграции AppsFlyer** в doc-комментарии
  `AttributionResolver` и в README: токен опознания лежит в `deep_link_sub1`
  (дубль — `af_sub1`), а в `deep_link_value` бэкенд кладёт константу `handoff`.
  Кто копировал старый образец, получал строку `handoff` вместо токена.

## [0.5.0] — 2026-08-12

Паритет с Android SDK 0.5.0. Минор, а не патч: добавлена функциональность —
события прохождения воронки наружу, встроенный показ квиза, profile-id
подписочных платформ в URL страницы.

### Added
- **События воронки из WebView-моста** — `Web2App.setFunnelEventListener(_:)`.
  Наружу идут `quiz_start`, `quiz_screen_view`, `quiz_answer`,
  `quiz_email_submit`, `quiz_complete`, а также `paywall_result` со
  `status == "dismissed"`. Слушатель один на SDK, снимается передачей `nil`;
  колбэк вызывается на главном потоке.
- **`Web2App.openQuizEmbedded(quizURL:email:completion:)`** — открытие квиза
  встроенным WKWebView (тот же экран и тот же мост, что у пейвола). Принимает
  ГОТОВЫЙ URL квиза: ручки резолва URL по ID на бэкенде нет, аналога
  `openWebPaywallEmbedded(paywallId:)` тут не существует. Результат — не оплата,
  а факт закрытия: `QuizResult.closed(reason)` с `QuizCloseReason.page` /
  `.user` / `.paid`, либо `.unavailable` (SDK не сконфигурирован — экран не
  показали). Событие `quiz_complete` окно НЕ закрывает: квиз ведёт дальше.
  Право в квиз-режиме SDK не поллит — за грантом идите в `entitlement`.
- **profile-id подписочных платформ в URL** — у всех методов открытия (и
  пейвола, и квиза) появились опциональные `adaptyProfileId:` /
  `revenuecatProfileId:`. SDK дописывает их в URL страницы как
  `adapty_profile_id` / `revenuecat_profile_id`; связку с guid делает сервер
  сам, отдельную ручку звать не надо.

### Changed
- ⚠ **Изменение поведения моста.** Раньше ЛЮБОЕ распознанное событие моста
  закрывало встроенный WebView. Теперь закрывают ровно два —
  `paywall_result` со `status == "success"` и `close`; всё остальное (включая
  `paywall_result:dismissed` и все `quiz_*`) окно не трогает. Незнакомые события
  игнорируются, поэтому старые интеграции работают без правок.
- ⚠ **Порядок параметров у методов открытия.** `adaptyProfileId:` и
  `revenuecatProfileId:` встали ПЕРЕД `completion:`. У обоих есть значение по
  умолчанию (`nil`), так что вызов с явными метками аргументов
  (`openWebPaywall(paywallURL:…, completion:)`) продолжает компилироваться —
  в Swift метки обязательны, поэтому «позиционного» слома, как в Android-версии,
  тут нет. Но если вы храните метод как значение (`let f = Web2App.openWebPaywall`)
  или передаёте его как замыкание — тип функции изменился, место придётся
  поправить.

### Fixed
- **Починен парс ответа `GET /public/handoff/resolve?code=`**: guid лежит внутри
  обёртки `{"success":true,"data":{...}}`, а читался с верхнего уровня. Фикс
  приехал уже после тега `0.4.3` и в предыдущий релиз не попал.

### Fixed
- **Safari-режим: свайп-закрытие шторки «терял» completion навсегда** —
  SFSafariViewController теперь показывается `.fullScreen` (свайп недоступен),

  completion первого вызова: предыдущий презентер корректно завершается.

- Embedded-режим: окно поллинга после события `close` выровнено с окном
  после успеха (10 попыток × 1с) — закрывший юзер с медленным вебхуком
  больше не получает мгновенный `.notPaid`.

### Added
- `PaywallResult.unavailable` — «пейвол не был показан» (SDK не
  сконфигурирован / платформа без UIKit / не разрезолвился paywallId);
  раньше это маскировалось под `.notPaid`.
